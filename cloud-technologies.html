Практический разбор: Главная

Облачная инфраструктура объединяет дата-центры, вычисления, хранилища, сети и прикладные сервисы. Рассматривать её удобнее как цепочку: устройство, канал связи, точка входа, приложение, данные и резервный контур. Изменение одного слоя влияет на остальные, поэтому решения стоит оценивать системно.

При разборе темы «Главная» сначала зафиксируйте цель: какой пользовательский сценарий должен работать, какие данные участвуют и что считается приемлемым результатом. Затем перечислите ограничения по задержке, доступности, конфиденциальности и бюджету. Такой порядок помогает выбрать минимально достаточную архитектуру вместо набора несвязанных сервисов.

Для оценки результата используйте не один показатель, а сочетание технической метрики и пользовательского эффекта. Снижение времени ответа может быть бесполезным, если выросла частота ошибок; уменьшение цены ресурса невыгодно, если оно увеличивает простой. Сравнение проводите на одинаковом наборе сценариев и с одинаковыми условиями нагрузки.

  • Проверить исходные требования и критерии готовности для темы «Главная».
  • Сохранить измерения до и после изменения, включая ошибки и стоимость.
  • Назначить ответственного за регулярный пересмотр настроек и документации.

Практический разбор: Что такое облака

Облачная модель предоставляет измеряемые ресурсы по сети и позволяет быстро выделять или освобождать их. За автоматическим интерфейсом работают физические площадки, пулы оборудования, системы изоляции, учёт потребления и управление доступом. Клиенту важно понимать, какие задачи остаются на его стороне.

Практическая проверка для темы «Что такое облака» начинается с небольшого стенда. Измерьте обычную нагрузку, создайте контролируемый отказ или изменение конфигурации и сравните результат с заранее установленным критерием. Запишите настройки, версии компонентов и наблюдения: без этого эксперимент трудно повторить, а выводы нельзя надёжно использовать при дальнейшем развитии.

Особое внимание уделите границам ответственности и данным, которые проходят через компонент. Определите владельца конфигурации, порядок выдачи прав, место хранения журналов и срок хранения результатов. Любое автоматическое действие должно оставлять понятный след, а опасные изменения — иметь ограничение по масштабу и проверенный способ отмены.

  • Проверить исходные требования и критерии готовности для темы «Что такое облака».
  • Сохранить измерения до и после изменения, включая ошибки и стоимость.

Раздел 03 · Модели сервиса

IaaS, PaaS, SaaS и другие «as-a-Service»

Облачные сервисы классифицируют по уровню абстракции: от «голого железа» до готового приложения. Чем выше уровень, тем меньше контроля, но и меньше забот о инфраструктуре.

🖥IaaS

Infrastructure as a Service — виртуальные машины, сети, хранилища. Максимальный контроль, вы управляете ОС и всем стеком.

  • AWS EC2, Google Compute Engine
  • Yandex Compute Cloud, VK Cloud
  • Гибкость и масштаб

⚙PaaS

Platform as a Service — готовая платформа для разработки и деплоя. Управляете только кодом, платформа берёт на себя ОС, runtime, масштабирование.

  • Heroku, Google App Engine
  • Azure App Service
  • Быстрый старт, фокус на коде

📱SaaS

Software as a Service — готовые приложения. Используете через браузер, платите за подписку. Ничего не администрируете.

  • Google Workspace, Microsoft 365
  • Salesforce, Zoom, Slack
  • Мгновенный старт

⚡FaaS / Serverless

Function as a Service — запуск отдельных функций без управления серверами. Оплата за вызовы и время выполнения.

  • AWS Lambda, Azure Functions
  • Yandex Cloud Functions
  • Мгновенное масштабирование

📦CaaS / Containers

Container as a Service — управляемый Kubernetes и среда запуска контейнеров.

  • AWS EKS, Google GKE, Azure AKS
  • Yandex Managed Kubernetes
  • Портативность

🗄DBaaS

Database as a Service — управляемые базы данных. Бэкапы, репликация, патчи — на стороне провайдера.

  • AWS RDS, Aurora
  • Managed PostgreSQL, MySQL
  • Автоматизация рутины

Различия определяются распределением обязанностей, а не только интерфейсом. Услуги могут сочетать признаки нескольких моделей, поэтому следует изучать конкретные условия обслуживания.

Сравнение проводите на одинаковом наборе сценариев и с одинаковыми условиями нагрузки.

Раздел 04 · Развёртывание

Модели развёртывания облака

Облака различаются по тому, кто владеет инфраструктурой и кто имеет к ней доступ. Публичные, частные, гибридные, мультиоблачные и community-модели решают разные задачи бизнеса и регулирования.

🌍Публичное облако

Инфраструктура принадлежит провайдеру, доступна всем через интернет. Плюсы: масштаб, цена, скорость. Минусы: зависимость от провайдера.

🏢Частное облако

Развёртывается для одной организации. Контроль и безопасность выше, но требует инвестиций и команды. Примеры: OpenStack, VMware vSphere.

🔀Гибридное облако

Комбинация частного и публичного. Критичные данные — внутри, эластичные нагрузки — в публичном. Требует зрелых процессов.

🌈Мультиоблако

Использование двух и более публичных провайдеров (AWS + Azure). Снижает риски vendor lock-in, но усложняет управление.

👥Community Cloud

Разделяется между организациями с общими задачами (например, госсектор, банки, научные центры).

🛰Распределённое

Геораспределённая инфраструктура с вычислениями ближе к пользователю (edge). Пример: AWS Local Zones, Yandex Edge.

Публичные, частные, гибридные и multi-cloud-среды отличаются размещением ресурсов, владением и способом интеграции. Несколько сред дают гибкость, но усложняют идентификацию, наблюдаемость, сетевые маршруты и учёт затрат. Архитектура должна объяснять, почему каждому типу данных или приложения выбрано именно такое размещение.

Контейнеризация и Docker

Контейнеры упаковывают приложение вместе с его зависимостями в изолированный образ. Один и тот же образ работает на ноутбуке разработчика, в тестовой среде и в проде. Это стало стандартом современной разработки.

🐳Docker

Самая популярная платформа контейнеризации. Dockerfile описывает образ, docker run запускает контейнер, Docker Hub — реестр образов.

🔒Изоляция

Namespaces (изоляция процессов, сети, ФС) и cgroups (лимиты CPU, RAM). Ядро общее с хостом.

🌐Реестры

Docker Hub, GitHub Container Registry, AWS ECR, Yandex Container Registry. Хранение и раздача образов.

Когда контейнеров сотни и тысячи, ими нужно управлять. Kubernetes автоматизирует развёртывание, масштабирование, самовосстановление и балансировку контейнерных приложений.

Декларативное описание желаемого состояния приложения. Rolling update, откаты, реплики.

🌐Services

ClusterIP, NodePort, LoadBalancer, Ingress. Абстракция доступа к подам.

📈HPA

Horizontal Pod Autoscaler — автомасштабирование по CPU, памяти или кастомным метрикам.

Практический разбор: Serverless

Serverless скрывает обслуживание серверов и запускает код по событию или запросу. Оплата часто связана с количеством вызовов и временем исполнения, поэтому модель подходит для переменной нагрузки.
